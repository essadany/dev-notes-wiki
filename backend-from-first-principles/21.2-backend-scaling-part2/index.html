    21.2. Scalabilité Backend & Performance Engineering (Partie 2)¶

    Après avoir vu dans la Partie 1 les métriques de base (P99, latence, headroom) et la différence entre vertical et horizontal scaling, on plonge ici dans les briques d'architecture concrètes : Statelessness, Load Balancers, Scalabilité BDD, CDNs, Edge Computing, Traitements Asynchrones, Microservices et Serverless !

    🔄 1. Le Prérequis Absolu du Horizontal Scaling : Le Statelessness (Sans État)¶

    La scalabilité horizontale consiste à multiplier les instances de notre serveur (Serveur A, B, C) exécutant le même code. Mais pour que cela fonctionne sans bugs imprévisibles, l'architecture doit impérativement respecter la propriété de Statelessness.

    💡 Définition : Un serveur est stateless (sans état) si aucune instance ne conserve de donnée exclusive en mémoire vive ou sur son disque local. N'importe quel serveur doit pouvoir traiter n'importe quelle requête avec exactement le même résultat.

    Le Piège du Serveur Stateful en Cluster¶

    Si le serveur A stocke une session d'authentification dans un tableau JS en RAM :

                                   ┌────────────────────────────────┐
                               │     LOAD BALANCER              │
                               └──────────────┬─────────────────┘
                                              │
                    ┌─────────────────────────┼─────────────────────────┐
                    │ Requête 1 (Login)       │ Requête 2 (Profil)      │
                    ▼                         ▼                         ▼
      ┌──────────────────────────┐ ┌──────────────────────────┐ ┌──────────────────────────┐
      │        SERVEUR A         │ │        SERVEUR B         │ │        SERVEUR C         │
      ├──────────────────────────┤ ├──────────────────────────┤ ├──────────────────────────┤
      │ • Reçoit Login           │ │ • Reçoit Requête Profil  │ │ • Aucune donnée en RAM   │
      │ • Stocke session en RAM  │ │ • Vérifie sa RAM local   │ │                          │
      │   [User123 -> Authent]   │ │   -> Session introuvable!│ │                          │
      │ • Renvoie Cookie         │ │ • ERREUR 401 UNAUTHORIZED│ │                          │
      └──────────────────────────┘ └──────────────────────────┘ └──────────────────────────┘

    ❌ Résultat : L'utilisateur se connecte sur A, mais dès que sa requête suivante atterrit sur B, il se fait rejeter avec une erreur 401 frustrante !

    La Règle d'Or : Externaliser Tout l'État¶

    Pour garantir le statelessness, on applique une règle stricte : aucun état local.

    Type de donnée Mauvaise pratique (Stateful) Bon réflexe (Stateless)
    Sessions Auth Stockées en mémoire RAM du serveur Redis (Base in-memory centralisée accessible par A, B, C)
    Fichiers / Uploads Sauvegardés sur le SSD local (/uploads) Object Storage (Amazon S3, Cloudflare R2, MinIO)
    Bases de Données Fichier SQLite local sur l'instance BDD Centralisée (PostgreSQL / RDS externe)

    ⚖️ 2. Les Load Balancers & leurs Algorithmes de Routage¶

    Sans Load Balancer (LB), la scalabilité horizontale est impossible. Le Load Balancer est le "chef d'orchestre" situé entre Internet et nos instances de serveurs d'application.

     [ Utilisateurs / Internet ]
              │
              ▼
    ┌──────────────────┐
    │  LOAD BALANCER   │ ── (Choisit l'instance optimale via un algorithme)
    └─────────┬────────┘
              ├───────────────────────┬───────────────────────┐
              ▼                       ▼                       ▼
      ┌──────────────┐        ┌──────────────┐        ┌──────────────┐
      │  Instance A  │        │  Instance B  │        │  Instance C  │
      └──────────────┘        └──────────────┘        └──────────────┘

    Panorama des Algorithmes de Load Balancing¶

    1. Round Robin (Tournant simple) :
    2. Principe : Distribue les requêtes en boucle (A $ ightarrow$ B $ ightarrow$ C $ ightarrow$ A...).
    3. Ideal pour : Des requêtes homogènes (ex: simples SELECT) sur des serveurs de capacité identique.

    4. Limite : Si une requête lourde (ex: 2s d'écriture BDD + appel API tiers) atterrit sur A et que d'autres requêtes s'y accumulent, A risque le crash.

    5. Weighted Round Robin (Pondéré) :

    6. Principe : Assigne un poids selon la puissance matérielle (ex: Serveur A avec 8 Go RAM / 4 vCPU reçoit 2x plus de requêtes que B et C avec 4 Go RAM / 2 vCPU).

    7. Least Connections (Moins de connexions actives) :

    8. Principe : Oriente la requête vers le serveur qui maintient le moins de connexions HTTP/TCP actives à l'instant T.

    9. Ideal pour : Des API avec des temps de traitement très variables (requêtes légères vs traitements lourds).

    10. Weighted Least Connections / Least Response Time / Resource-Based :

    11. Variantes avancées prenant en compte la latence de réponse moyenne ou l'utilisation courante CPU/RAM.

    Health Checks : La Détection Automatique de Pannes¶

    Pour éviter de router du trafic vers une instance plantée : * Le Load Balancer envoie un test discret (ex: GET /health) chaque seconde à chaque serveur. * Si le serveur A ne répond pas avec un 200 OK (ex: renvoie 502 Bad Gateway ou timeout), il est blacklisté instantanément. * Les utilisateurs sont redirigés vers B et C. Dès que A s'en remet et renvoie à nouveau 200 OK, il réintègre le cluster automatiquement.

    🗄️ 3. La Scalabilité des Bases de Données (La partie Stateful)¶

    Alors que nos serveurs d'application se multiplient facilement grâce au statelessness, la base de données reste le composant stateful le plus difficile à scaler, car les données doivent rester strictement cohérentes.

    A. Les Read Replicas (Répliques en Lecture)¶

    Dans la plupart des applications SaaS, 70% à 90% du trafic consiste en des requêtes de lecture (SELECT).

                                  [ SERVEURS BACKEND ]
                                │              │
                (Écritures 30%) │              │ (Lectures 70%)
                                ▼              ▼
                      ┌──────────────────┐    ┌──────────────────┐
                      │ PRIMARY (Master) │    │  READ REPLICAS   │
                      │ (Writes / SQL)   │    │  (Replicas 1,2)  │
                      └────────┬─────────┘    └──────────────────┘
                               │ (Replication Lag ~200ms)
                               └──────────────────────►
    • Fonctionnement : Un serveur Primary gère 100% des écritures (INSERT, UPDATE, DELETE). Ses données sont répliquées vers plusieurs Read Replicas dédiés uniquement aux lectures.
    • Avantage : Réduction massive de la charge sur le serveur principal et baisse de la latence en plaçant des répliques proches géographiquement des utilisateurs (ex: Primary aux US, Replicas en Inde et en Europe).
    • Le Problème du Replication Lag : La donnée voyage dans des câbles sous-marins. Il existe un délai physique de réplication (ex: 200 ms).
    • Cas critique : L'utilisateur met à jour son profil ($ ightarrow$ écriture sur le Primary US) puis rafraîchit immédiatement la page ($ ightarrow$ lecture sur le Replica Inde qui n'a pas encore reçu le changement). Il voit son ancien nom !
    • Solutions : Router temporairement les lectures post-écriture vers le Primary, suspendre légèrement la requête de lecture le temps du lag, ou adapter l'UX du front-end.

    B. Le Sharding (Partitionnement Horizontal)¶

    Quand une table dépasse des milliards de lignes (ex: table orders sur Amazon) et qu'un seul serveur BDD étouffe sous le volume :

    • Principe : On découpe physiquement la table sur plusieurs instances BDD distinctes grâce à une Sharding Key (ex: partitionnement par plages de dates Jan-Juin vs Juil-Déc, ou par user_id).
    • Gain : Division de la taille des tables par instance, réduction drastique du temps de requête (Query Latency) et répartition des IOPS.

    C. Bases de Données Distribuées Modernes¶

    Aujourd'hui, il est déconseillé de créer sa propre infrastructure de sharding manuelle. On privilégie les Distributed Databases gérées : * Neon (PostgreSQL Serverless écrit en Rust). * PlanetScale (MySQL basé sur Vitess). * CockroachDB / YugabyteDB.

    🌐 4. CDN (Content Delivery Networks) & Edge Computing¶

    Vaincre la Vitesse de la Lumière¶

    La lumière voyage à ~200 000 km/s dans la fibre optique. Un aller-retour (RTT) Tokyo $\leftrightarrow$ Virginie du Nord (US East 1) prend 100 ms minimum, rien qu'en transport réseau !

    Si l'on ajoute le parsing JSON, les requêtes BDD (50-100 ms) et les appels d'API externes (200 ms), la latence perçue grimpe vite à 500-800 ms.

     [ Client (Tokyo) ] ─────── 2 000 km (2 ms) ───────► [ CDN Edge Node (Tokyo) ]  ─── (Réponse instantanée)
        │
        └───────────────── 20 000 km (100 ms RTT) ─────────────────────────────────► [ Serveur US East ]

    Le Rôle des CDN & Points of Presence (PoPs)¶

    Les CDN (ex: Cloudflare, AWS CloudFront) placent des serveurs appelés Edge Locations ou PoPs au plus près des utilisateurs (ex: à Tokyo). 1. Contenu Statique : Caching des bundles JS/CSS, images, vidéos, polices. 2. Réponses API : Caching de catalogues produits peu changeants (avec invalidation par tags). 3. Protection DDoS : Absorption de Terabits de trafic malveillant au niveau du CDN avant qu'il n'atteigne nos serveurs.

    L'Ère du Edge Computing¶

    Le Edge Computing ne se contente plus de servir des fichiers statiques : il exécute du code au plus près de l'utilisateur (ex: Cloudflare Workers basés sur les V8 Isolates de Chrome).

    • Cas d'usage numéro 1 : L'Authentification au Edge : Rejeter les requêtes non authentifiées avec un 401 Unauthorized en 2 ms au niveau du PoP de Tokyo, au lieu de gaspiller 100 ms de voyage réseau et des ressources serveur aux US.
    • Limites du Edge : Contraintes de ressources (RAM/CPU limitées à 1 Go / 1 vCPU), absence de système de fichiers local et indisponibilité des connexions TCP persistantes traditionnelles.

    ⏳ 5. Traitements Asynchrones & File d'Attente (Task Queues)¶

    Pour offrir une application ultra-snappy, il faut réduire la latence perçue par l'utilisateur en sortant du cycle de requête synchrone tout ce qui n'a pas besoin d'être exécuté immédiatement.

    Exemple Concret : L'Invitation d'un Membre d'Équipe¶

      APPROCHE SYNCHRONE (Lente - 400ms) :
  User ──► API ──► Write BDD (100ms) ──► Appel API SendGrid (300ms) ──► Response 200 OK (400ms)

  APPROCHE ASYNCHRONE (Snappy - 100ms) :
  User ──► API ──► Write BDD (100ms) ──► Push Job dans Redis Queue ──► Response 200 OK (100ms)
                                                │
                                                ▼
                                    [ Consumer / Worker ] ──► Appel SendGrid (en arrière-plan)

    Les 4 Cas d'Usage Idéaux de l'Asynchronisme¶

    1. Envoi d'Emails / Notifications (SendGrid, Resend).
    2. Traitements Médias (Encodage vidéo YouTube, redimensionnement d'images, génération de sous-titres).
    3. Suppression de Compte (Delete Account) : La purge en cascade de millions de lignes dans 8 tables BDD prend 8 secondes. En asynchrone, on répond 200 OK en 100 ms et le Worker nettoie la BDD en tâche de fond.
    4. Tâches Récurrentes (Cron Jobs) : Nettoyage nocturne, rapports hebdomadaires.

    Technologies populaires : Redis + BullMQ (Node.js), RabbitMQ, AWS SQS.

    🧩 6. Microservices vs Monolithe : La Réalité du Terrain¶

    On entend souvent que les microservices sont indispensables pour scaler. C'est une idée reçue !

    ⚠️ Vérité : Les microservices ne servent pas d'abord à scaler la performance des machines, mais à scaler la performance des équipes humaines quand elles dépassent 100 à 500 développeurs.

    Tableau Comparatif : Monolithe vs Microservices¶

    Critère Monolithe (Single Deployable Unit) Microservices (Services Indépendants)
    Complexité Simple à développer, tester et déployer Très complexe (Gestion du réseau, pannes)
    Déploiement Un seul process à déployer Déploiements indépendants par équipe
    Scalabilité Globale (on scale tout le monolithe) Granulaire (ex: scaler le service paiement seul)
    Stack Technique Unique (ex: tout en Node.js ou Go) Polyglotte (Node.js pour le parsing, Rust pour la perf)
    Communication Appels de fonctions en mémoire Appels réseau (gRPC / HTTP REST / Kafka)
    Debugging Stack trace directe dans un seul log Traces distribuées indispensables (Jaeger/OpenTelemetry)

    ☁️ 7. Serverless Computing (FaaS)¶

    Le Serverless (AWS Lambda, Cloudflare Workers, Vercel) affranchit l'ingénieur de la gestion des VMs (Ubuntu, Docker, Nginx).

    Le Changement de Modèle¶

    • Traditionnel (Serverful) : On loue une VM 24h/24 (ex: 4 Go RAM). Qu'il y ait 0 ou 1000 requêtes/sec, on paie le serveur en continu.
    • Serverless : On fournit uniquement du code (fonctions). L'API Gateway intercepte l'événement HTTP et instancie une machine à la volée. On ne paie strictement que les millisecondes d'exécution CPU.
      Requête HTTP ──► [ API Gateway ] ──► Instantie la fonction ──► Exécute le code ──► Détruit l'instance

    Le Défi Majeur : Le Cold Start (Démarrage à Froid)¶

    Puisqu'aucun serveur n'attend les requêtes à l'avance, le premier appel subit un délai d'initialisation (boot de l'environnement + chargement du runtime) appelé Cold Start. * Solutions modernes : MicroVMs ultra-rapides (AWS Firecracker), V8 Isolates (boot en 0-5 ms), et pings de chauffe automatiques (warming pings).

    🎯 8. Les 5 Règles d'Or de l'Ingénieur Backend¶

    Pour conclure ce cours sur la performance et le scaling, voici les 5 principes directeurs à garder en tête au quotidien :

    1. 📏 Mesurer Avant Tout (Measure First) : Ne devinez jamais où se trouve le bottleneck. Utilisez l'observabilité (Prometheus, Grafana, New Relic, Tracing) pour identifier scientifiquement la cause de la lenteur avant de coder la moindre solution. Évitez l'optimisation prématurée !
    2. 🧹 Préférer les Solutions Simples : Un monolithe bien structuré avec un index B-Tree PostgreSQL est 100 fois plus simple et performant qu'une architecture microservices mal maîtrisée avec Redis et Kafka.
    3. 📈 Scaler Pour Vos Besoins Réels : Ne concevez pas votre système pour 1 milliard d'utilisateurs le premier jour. Concevez pour votre échelle actuelle avec une marge de sécurité raisonnable (headroom de 20-40%).
    4. 👁️ L'Observabilité dès le Jour 1 : Installez des logs structurés (JSON), des métriques et du tracing dès le démarrage du projet.
    5. 🧠 Le Mindset de Performance : La performance est un apprentissage continu. Observez la réaction de vos systèmes sous charge, ajustez, et construisez des architectures capables de dégrader élégamment leur service en cas de panne.
