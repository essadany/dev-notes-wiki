# 21. Migrations de base de données

> 🎯 **Résumé.** Sans schéma versionné, deux développeurs appliquent manuellement des `ALTER TABLE` différents et la prod diverge de dev. On versionne chaque changement dans des migrations exécutées automatiquement au déploiement, avec le motif *expand/contract* pour rester compatible avec l'ancienne version du code. Le piège : modifier une migration déjà déployée, ou faire confiance à `ddl-auto=update` en production.

---

## 🧭 1. Contexte

**Principe** : le schéma est versionné dans le code et appliqué automatiquement.

| Stack | Outil |
|---|---|
| Spring | Flyway ou Liquibase |
| Django | `makemigrations` / `migrate` |
| Laravel | `php artisan migrate` |
| Node | Prisma Migrate, TypeORM migrations, Knex |
| Python (SQLAlchemy) | Alembic |

**Bonnes pratiques** : ne jamais modifier une migration déjà déployée ; migrations compatibles avec l'ancienne version du code (pattern *expand/contract* : ajouter, migrer, puis supprimer) pour déployer sans coupure ; `ddl-auto=update` à éviter en production.

---

## 💻 2. Exemples techniques

La séquence Flyway ci-dessous ajoute une colonne, la remplit, puis ne la rend obligatoire que dans une migration suivante : l'ancien code continue de fonctionner pendant le déploiement.

```sql
-- V1__create_users.sql
CREATE TABLE users (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email      VARCHAR(255) NOT NULL UNIQUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- V2__add_display_name_expand.sql
ALTER TABLE users ADD COLUMN display_name VARCHAR(255);
UPDATE users SET display_name = split_part(email, '@', 1) WHERE display_name IS NULL;

-- V3__display_name_contract.sql
ALTER TABLE users ALTER COLUMN display_name SET NOT NULL;
```

Avec Django, `makemigrations` génère le fichier versionné et `migrate` l'applique ; une donnée backfillée passe par une opération `RunPython` réversible.

```python
# users/migrations/0002_user_display_name.py
from django.db import migrations, models


def set_default_display_name(apps, schema_editor):
    User = apps.get_model("users", "User")
    User.objects.filter(display_name__isnull=True).update(display_name="utilisateur")


class Migration(migrations.Migration):
    dependencies = [("users", "0001_initial")]

    operations = [
        migrations.AddField(
            model_name="user",
            name="display_name",
            field=models.CharField(max_length=255, null=True, blank=True),
        ),
        migrations.RunPython(set_default_display_name, migrations.RunPython.noop),
    ]
```

En production avec Spring Boot, Flyway est le seul outil autorisé à écrire dans le schéma : Hibernate se contente de le valider.

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate
  flyway:
    enabled: true
    locations: classpath:db/migration
    baseline-on-migrate: false
```
